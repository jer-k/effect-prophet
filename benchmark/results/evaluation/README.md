# Stage H public evaluation benchmark review

This directory indexes the reviewed native-architecture public evaluation run. The result is descriptive timing evidence, not a performance ranking, universal speed claim, or statistical calibration study. The full raw samples, correctness records, failed cases and environment manifest live in the promoted [native Linux/arm64 snapshot](../baselines/stage-h-evaluation-native-arm-m4-pro/report.md) (git `85139681`, clean working tree, Apple M4 Pro, release WASM and pinned Prophet 1.4.0).

Nine of fourteen cases passed both correctness gates and were timed; five feature-bearing **flat** cases were not timed. Their point-fold forecasts diverged by up to 21.17 (96-row recipe) and 21.08 (256-row recipe) target units; the respective overall MAEs were 11.12 vs 0.068 and 10.46 vs 0.052 (Effect vs Python). This is a correctness discrepancy to investigate separately, **not** a performance result or permission to relax the tolerance. Both languages passed the declared row identity/count/finite checks, so it is not an alignment issue. The successful linear/logistic point folds differed by at most 0.00057. The three-candidate linear search recorded the designed missing-capacity failure; its remaining candidates produced a selected holdout report. The revised logistic search candidates both completed after the initial 0.05-prior candidate failed Python fitting during a provisional, ignored run.

Eligible example **absolute warm medians** (four timing samples each per implementation, milliseconds): linear point CV 5.994 (Effect) / 33.606 (Python), logistic point CV 4.333 / 24.701, 256-row logistic point CV 16.518 / 50.828, and three-candidate linear search with one recorded expected failure 9.669 / 71.476. These are not equivalent-work ratios; small samples do not support tail claims. The comparison class is `different-public-work`: Python requires a previously fitted mutable model and uses vectorized uncertainty; Effect refits sequentially and uses scalar simulation. Python baselines, search and final report assembly are explicit application loops, not Prophet APIs. Ineligible cases have no timing summaries; do not interpolate timings for them. RSS is a worker high-water mark, excludes Python CmdStan children, and is not heap/WASM-only allocation or a RAM ranking.

Run `npm run benchmark -- --case <case-id>` after a release-image rebuild to reproduce a subset. Run `npm run benchmark` for the complete suite, then review `report.md`, `report.json`, `eligible-cases.json`, `cases.json`, `manifest.json`, both adapter records and `records.jsonl` before promoting via `npm run benchmark:baseline -- <run-id> <baseline-id>`.
