## Exactly what a fold sees

For cutoff `c` and fixed positive elapsed horizon `H`, train on `timestamp <= c` and assess on `c < timestamp <= c+H`. The cutoff may lie between observations. Each assessment forecast is attached by original history index; `horizonMs = timestamp−c`, never zero. An assessment timestamp can occur in several overlapping folds, representing distinct out-of-sample forecasts. Explicit cutoffs without an assessment row are invalid; generated cutoffs walk backward and adjust around gaps as in Prophet. Durations are integer milliseconds, not calendar days/months or a schedule generator. [The caller](../decisions/data-preparation-boundary.md) owns timezones, omitted observations, future schedules and known future inputs.

| Potential leak                              | Training-fold policy                                                                                                                                                                          | Assessment policy                                                                                                                                                      |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Target values and target scaling            | Include only the training prefix; compute scaling, optimizer initialization and MAP noise with that prefix.                                                                                   | Preserve held-out value **only as actual**, never as prediction input.                                                                                                 |
| Regressor normalization and condition masks | Resolve transformations and automatic feature selection from the fold's training rows.                                                                                                        | Supply known future regressor/condition values unchanged; no target-based inference.                                                                                   |
| Automatic seasonalities and changepoints    | Resolve anew in ordinary `fit` using training timestamps only. The planner conservatively budgets `"auto"` seasonality periods without enabling them.                                         | Assessment timestamps never enable training features or place candidates.                                                                                              |
| Explicit changepoints                       | Retain only points **strictly before the last observed training timestamp** (Prophet 1.4.0's actual `prophet_copy` filter, not its `<= cutoff` comment). Empty is valid; no fabricated point. | Points at/after that last observed training timestamp are removed even when before a between-observations cutoff.                                                      |
| Events/static definitions                   | Reuse declared configuration; evaluate training features only on training rows.                                                                                                               | Known event calendar/condition state may be used for prediction; it does not reveal held-out targets.                                                                  |
| Logistic capacity/floor                     | Fit normalization and bounds only from the training prefix.                                                                                                                                   | Preserve row-specific known capacity/floor while dropping only target; invalid/missing bounds fail before WASM.                                                        |
| Uncertainty seeds                           | Root seed and versioned plan identity determine each fold seed; no evolving shared RNG.                                                                                                       | Draws use the fitted fold and complete future row values, never assessment targets. Width and sample count describe Monte Carlo settings, **not coverage guarantees**. |

A manually supplied complete history can include information known only later in its static configuration or future covariates; the package cannot prove availability in real time. Applications must design a genuine retrospective feature pipeline. Point and interval cross-validation tests poison held-out targets and compare the first fold's forecasts and intervals with an independent prefix fit/simulation. The root seed is expanded with the validated full plan, simulation identity, optional candidate ID (empty for direct CV) and cutoff using the versioned `effect-prophet-eval-seed-v1` schedule. This is same-build replay, not Python-seed equivalence.

## Metric and comparison meaning

Errors compare held-out `actual` to fold-specific point `predicted`. MAE/RMSE are observation-unit magnitudes; MSE is squared units; MAPE/MDAPE/sMAPE are **ratios**, not multiplied by 100. Percentage division by an exact-zero actual fails by default; explicit exclusion reports included/excluded counts and fails on an all-excluded bucket. `0/0` sMAPE contributes zero. Coverage includes both interval endpoints and is available only for interval results. Coverage is empirical marginal interval inclusion on these particular folds: it does not establish calibration for new data, simultaneous path coverage or a Bayesian coefficient posterior. See [Stage G limitations and evidence](uncertainty.md) and [empirical validation](../validation/uncertainty.md).

`performanceMetrics(result, { metrics, aggregation, mapeZeroActual? })` takes trusted cross-validation rows and returns a tagged `rows`, `horizons`, `rolling` or `overall` report with finite scores and actual `rowCount` per bucket. `rows` retains fold/input order; `horizons` and `rolling` sort ascending elapsed integer milliseconds, with an output per distinct right-edge horizon. A count window requires a positive integer no greater than the row count; a fraction window uses `max(1, floor(fraction × rowCount))` for `0 < fraction <= 1`. Percentage metrics give bucket-local `includedCount`/`excludedCount`; the omitted zero policy defaults to `"error"`. Malformed options return `InputValidationError(input="evaluation-metrics")`; unavailable coverage, exact-zero actuals, all-excluded buckets and nonfinite arithmetic return `EvaluationMetricError` with metric, aggregation, bucket index and stage. No requested metric disappears. The operation does not fit, simulate, call WASM, mutate input or create per-row spans.

Overall metrics weight every forecast instance once; exact-horizon metrics group equal elapsed milliseconds; right-aligned rolling metrics use whole horizon groups until at least the configured number of instances. Rolling windows may contain **more** than the target count. This is an intentional, explicit difference from Prophet 1.4.0's fractional weighted boundary for rolling means and its distinct rolling median selection. The pinned `evaluation-metrics.json` fixture compares all seven release equations on distinct-horizon nonzero rows in row, exact-horizon, rolling and overall modes. Additional tests cover the deliberate differences: Python silently removes coverage when bounds are absent, skips MAPE for any `abs(actual) < 1e-8`, and treats exact `0/0` sMAPE as zero; here missing coverage fails, near-zero nonzero actuals are retained, exact zero follows an explicit policy shared by MAPE/MDAPE, and `0/0` sMAPE remains zero. Python's rolling `1` and our overall mode both weight all rows, but an overall report has no fabricated horizon. Scores are ratios rather than multiplied-by-100 percentages. There are no confidence intervals for metric estimates, significance tests or independent-series claims. `crossValidateBaseline(history, planSummary, definition)` reconstructs and checks the existing fold plan against complete history. Last-value, compensated training-mean and exact-lag seasonal-naive forecasts use each same fold's training rows; a missing exact lag fails the entire operation instead of changing denominators. `performanceMetrics` accepts baseline point rows under a distinct `baseline` source tag; coverage remains interval-only. `comparePerformance(modelResult, baselineResults, metricOptions)` checks identical plan, row ordering and actuals, computes one shared metric policy, and reports scores side by side, not a universal improvement. No relative skill or significance estimate is provided.

**Prophet 1.4.0 deviations:** Python `diagnostics.py` has no public last-observation, training-mean, exact-lag seasonal-naive or comparison API. These are explicit package extensions, not translated Python model families. We reuse the package's release-style rolling-origin cutoffs and forecast-instance rows, but require exact timestamp lags and all-or-nothing availability; we do not infer a calendar frequency, interpolate or drop unmatched rows. Python's `performance_metrics` also differs in rolling-window boundaries, MAPE zero handling and optional coverage as described above; both implementations assign zero to `0/0` sMAPE. The summary-driven baseline API checks plan/history consistency without model options; generated cutoffs must first be planned with the same complete options as model evaluation.

Model selection uses only development folds; the winning candidate is the finite minimum of a declared **overall point-error** metric, with input-order ties. Optional interval diagnostics cannot make coverage an implicit accuracy score. A separate one-time holdout operation fits the selected configuration on all development rows and predicts strictly later holdout rows. A lower development score is selection evidence, not final quality; repeated inspection of holdout outcomes defeats the one-time interpretation even if the API cannot detect it. The resulting JSON-compatible report can contain sensitive input/forecast values and belongs to the caller, never to span attributes or automatic logging.
