# Caller-owned data preparation and prediction schedules (EP-092)

**Status:** Accepted policy for the existing public API. No preprocessing or scheduling API is added.

## Decision

Applications turn their source data into complete, canonical, model-ready rows _before_ calling `fit` or `predict`. They decide which records to omit, how to handle duplicate records, how to aggregate and order data, how to convert source dates to UTC instants, which future instants to predict, and how to populate every required future covariate, condition, capacity and floor. The package parses and rejects malformed rows; it does not sort, drop, fill, impute, clip, aggregate, infer frequency, create calendars or repair rejected inputs. A missing/outlier target means the application omits the **entire observation**, not that it sends a row with a null target. Omitted rows are gaps, not zeros.

For accepted model-ready rows, continue to implement the supported mathematical features against the pinned Python Prophet 1.4.0 release. Matching the model does not require adopting Python's pandas ingestion rules. This decision preserves `decodeObservations`, `fit`, `decodePredictionRows` and `predict` as shipped and adds no service, dependency, error type, Rust operation or WASM ABI. Existing public/coarse Effect spans remain; source-adapter failures before `fit`/`predict` are outside library tracing.

## Why this differs from Python, and what still matches

The reference is unmodified [Python Prophet 1.4.0 `forecaster.py` at `abf69a215604afcaa7ecb4359f592d13bf6dea9f`](https://github.com/facebook/prophet/blob/abf69a215604afcaa7ecb4359f592d13bf6dea9f/python/prophet/forecaster.py). `preprocess` (around lines 1323–1341) drops null-`y` rows from **fitting**, requires two retained rows, but records every distinct input `ds` in `history_dates` _before_ dropping targets. `make_future_dataframe` (around 2180–2216) can use those dates for the last anchor, history output, and frequency inference from the last five dates. This package intentionally stores no second, dropped-row date history: omitting a row changes both the fit and the caller's explicitly chosen forecast schedule.

Python's `setup_dataframe` (around 318–408) uses pandas dates, stably sorts `ds` and accepts duplicates, checks configured regressors/conditions, and scales targets with training data. Our training rows require strictly increasing unique canonical UTC timestamps, finite values and strict booleans; prediction preserves order and duplicates, including complete rows with different feature values at the same time. Python accepts boolean-compatible `0`/`1` for conditions and generally ignores unrelated dataframe columns; our strict schema rejects unknown row keys and named feature misalignment. Python rejects an empty explicit prediction dataframe; our empty `predict` result succeeds after row syntax validation without inspecting model/runtime. Python can overwrite a supplied future floor in implicit-floor logistic mode; our contract rejects it instead. These are deliberate boundary differences, not numerical-fit parity claims.

Python's `initialize_scales`, `set_changepoints` and `fit` (around 410–505 and 1400–1454) derive transforms/candidates solely from fitted history; exact constant linear/flat histories use the `sigma_obs=1e-9` shortcut and logistic histories are optimized. The package keeps those distinctions on its supported MAP paths, but fitting optimizers and numerical failure states have their own documented differences. Python's `make_future_dataframe` (2180–2216) may infer a pandas frequency or default to daily; its output still does not invent future regressor/condition/capacity/floor values. Python [non-daily guidance](https://github.com/facebook/prophet/blob/abf69a215604afcaa7ecb4359f592d13bf6dea9f/docs/_docs/non-daily_data.md) recommends restricting predictions to observed support for sparse windows and using month-start schedules for monthly history. We adopt the guidance, not pandas' schedule generator.

As corroborating _design evidence_, [Prophet.rb's README at `646117343534ff36f9edc9bfd959c9405bf50777`](https://github.com/ankane/prophet-ruby/blob/646117343534ff36f9edc9bfd959c9405bf50777/README.md) demonstrates caller-authored Rover frames with `ds`/`y`, future `cap`/`floor`, explicit future regressor computation, monthly `MS` schedules and explicit outlier marking. It also has a simple hash API, a future-dataframe helper, and missing-data conveniences. It is **not** the compatibility target and does not justify copying its helpers, dataframe semantics or `Float::NAN` policy.

## Boundary and follow-up trigger

The application owns source parsing, exclusions, aggregation, sorting/deduplication, timezone/calendar choice, shock/outlier policy and reporting source failures. The package owns strict row/options parsing, model-specific training/prediction requirements, train-only derived state, fitting/prediction and typed failures. It never retries a rejected request after dropping a row. Syntax/ordering failure precedes options/model/backend work; accepted short histories can fail as `FittingError` after model-specific support checks. No current error classification is relaxed by this decision.

Forecast schedules remain explicit: adding `86_400_000` milliseconds is one elapsed UTC duration, **not** a local civil day or month. Month-start/end, weekday, timezone-aware and DST rules (including nonexistent/ambiguous civil times) must be chosen by the caller's calendar system. Future rows are enriched after choosing instants. The model has no retained history schedule to append or infer.

A package preprocessing adapter or schedule helper is **not approved**. Revisit only with recorded independent consumer friction, an exact follow-up ticket, explicit input/output and error policy, bounded counts/ranges, and chosen sorting, deduplication, missing-target, timezone/DST and complete-future-row semantics. A future adapter must parse into existing strict encoded rows, remain outside numerical/WASM code and trace only an actual integration operation; it must not silently change the core. See the [usage matrix and runnable example](../usage/data-and-edge-cases.md) for falsifiable current behavior.
