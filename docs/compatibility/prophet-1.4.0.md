# Python Prophet 1.4.0 compatibility contract

## Scope

`effect-prophet` targets observable numerical behavior from the unmodified Python
`prophet==1.4.0` release. The target is fixed; it is not the upstream `main` branch and does not
advance when upstream publishes a patch.

This is a capability-by-capability target, not a claim of blanket compatibility. The current
implementation includes additive or mixed flat, linear-piecewise, and logistic MAP lifecycles.
Linear fitting always uses MAP, including featureless and short-history requests. Broader Prophet model families remain outside this
implementation; linear and logistic fitted quality have separately declared acceptance contracts.
The package also implements seeded MAP uncertainty, rolling-origin evaluation, metrics, train-only
baselines, bounded model search and separate final-holdout reports. Until a checklist row has
compatible evidence, describe that capability as Prophet-inspired rather than Prophet-compatible.

Compatibility means matching documented, observable behavior where the checklist says that is
the target. It does not require Python method signatures, pandas dataframes, the CmdStanPy
backend, mutable model objects, plotting libraries, or interchange with Python's model JSON.
Those dimensions are separate and are either mapped below or deliberately different.

The release direction is Python 1.4.0 observable forecasting behavior **by default**, with improved
edge behavior considered through explicit opt-ins. Existing numerical/default differences below
remain current-source facts, not automatic permanent exemptions from investigation. The
[logistic reconciliation checkpoint](../validation/logistic-reconciliation.md) applies this direction:
logistic defaults now use automatic seasonalities and the shared Stan solver, compared against
Python under an output-first policy.

## Fixed reference identity

The baseline is the release identified by [`tools/prophet/reference.json`](../../tools/prophet/reference.json):

| Identity      | Value                                      |
| ------------- | ------------------------------------------ |
| Distribution  | `prophet`                                  |
| Version       | `1.4.0`                                    |
| Repository    | `https://github.com/facebook/prophet`      |
| Tag           | `v1.4.0`                                   |
| Source commit | `abf69a215604afcaa7ecb4359f592d13bf6dea9f` |

Verify any configured `@prophet` checkout against this exact source commit before using it.
A checkout name or upstream `HEAD` is not a baseline identity; the reference checkout was
verified at the pinned commit for this audit. Fixture generation remains tied to
[`tools/prophet/reference.json`](../../tools/prophet/reference.json), not to later upstream changes.
See the [tooling instructions](../../tools/prophet/README.md) for verification.

The audit covered the release's Python `Prophet` class, diagnostics, holiday helpers, model
serialization, utilities, Matplotlib/Plotly helpers, Python tests, and the authored workflows in
`docs/_docs`. Private implementation helpers were audited where they define preprocessing,
objective, optimization, prediction, or uncertainty behavior. They are behavioral references,
not Python API-shape commitments.

## Status vocabulary

- **implemented** — the current package exposes the behavior and has the evidence linked in the
  row. This does not imply broader Prophet parity.
- **partial** — a useful subset exists, but material Prophet behavior is absent or differs.
- **planned** — the roadmap assigns the capability, but the current package does not implement it.
- **intentionally-different** — the package deliberately uses a different contract or excludes
  the capability. The reason and any future review point are stated in the row.

“Not yet covered” means there is no current compatibility evidence. A roadmap entry is not
evidence.

## Implementation and evidence checkpoint

The checklist describes the current repository implementation, not a promise of blanket parity,
a published release, or independent statistical review.

- **EP-092 data preparation:** accepted ownership decision, complete-row omission recipe,
  UTC/calendar guidance, edge-policy matrix and public regressions are implemented.
  [Decision](../decisions/data-preparation-boundary.md), [guide](../usage/data-and-edge-cases.md),
  [built-package example](../../examples/data-policy.ts).
- **EP-096 training rows and linear MAP:** stable non-mutating sorting, independently retained
  duplicates, repeated generated changepoints and duplicate-aware evaluation/persistence are
  implemented. Additive and mixed linear MAP share the Stan-style objective, Newton/L-BFGS
  selection and original-initialization fallback. Obsolete linear controls and coordinate-model
  identities are rejected; new models preserve actual completion/attempt diagnostics without
  refitting. [Training-row lifecycle evidence](../../test/prophet-training-rows.test.ts),
  [optimizer lifecycle evidence](../../test/prophet-linear-optimizer.test.ts).
- **Linear fit-quality closeout:** the retained native-arm64 run qualifies **22 of 24** comparisons;
  two zero-span linear comparisons retain failures and no timing. Objective absolute `0.01`,
  normalized-noise absolute `0.0002` and other applicable quantity/lifecycle gates are unchanged.
  Stationarity remains visible but explicitly diagnostic-only under **EP-097**, not a small-KKT
  certificate. The original coordinate-exhaustion and stationarity-equality failures remain
  unchanged. [Approved policy](../decisions/linear-map-benchmark-acceptance.md),
  [retained dirty-tree snapshot](../../benchmark/results/retained/linear-map-fit-quality/2026-10-02T043132-582Z-4d661a06/README.md).
  The shared stationarity residual later began treating deltas within `1e-6` of zero as at their
  Laplace kink; that snapshot is not requalified.
- **Logistic reconciliation:** public defaults use automatic seasonalities, the shared Stan
  Newton/L-BFGS policy, Python's private no-point delta and its actual public rate fold. Logistic
  comparisons are **output-first**: forecasts, components, metadata, persistence and uncertainty
  replay gate each case; fitting objective, normalized noise and stationarity are reported and
  flagged for investigation. Linear still gates objective and noise. All 28 investigation cases and
  four controls pass in local dirty-tree evidence. The only flags, on `defaults-256`, are explained:
  unmodified Python itself diverges across `linux/amd64` and `linux/arm64` at the same L-BFGS step,
  by more than the threshold. The 12-row Newton residual gap reflects Effect stopping later with
  a lower objective. Same-input numerical tests remain exact; fit-endpoint tests report internal
  gaps. No retained baseline is claimed.
  [Policy](../decisions/logistic-map.md#benchmark-acceptance-output-first),
  [evidence and cross-CPU checks](../validation/logistic-reconciliation.md).
- **Stage G uncertainty:** scalar-path simulation, seeded replay, fixed-state distribution checks
  and descriptive fitted synthetic holdouts are implemented. EP-094's quantile-ordering correction
  has real native/WASM/public regressions and a separate passing correctness rerun; simulation
  identity is `prophet-map-scalar-xoshiro128ss-v2`, with unchanged sample draws. Independent
  interpretation review and universal calibration are not claimed.
  [Validation and limits](../validation/uncertainty.md),
  [original failure and separate rerun](../validation/uncertainty-benchmark-review.md).
- **Stage H evaluation:** planning, sequential point/seeded-interval folds, all seven metrics,
  aggregation, baselines, search and final-holdout/report persistence are implemented.
  **EP-095** isolated Python CV's dropped scaling: the
  [approved CV policy](../decisions/cross-validation-scaling.md) defaults to absmax
  independently of fit options, with an explicit minmax override. The current release-built
  dirty-tree benchmark reruns all 14 canonical evaluation cases and 22 direct flat cases
  under unchanged gates. At Jeremy's request, obsolete flat/evaluation failure snapshots
  and redundant diagnostic cases are removed; only current passing evidence is retained.
  Python's adapter explicitly maps numeric input columns to float64, matching JavaScript
  numbers without altering values or dataset bytes; constant minmax now exercises the full
  public JSON/fresh-restoration lifecycle instead of being excluded. The upstream model and
  serializer remain unmodified. This is bounded evidence, not general flat parity or a clean-tree release.
  [Current flat evidence and exclusions](../../benchmark/results/retained/flat-growth-and-evaluation/2026-10-02T210323-182Z-6cbae03d/README.md),
  [evaluation contract](../modeling/evaluation.md),
  [workflow](../usage/evaluation-and-tuning.md),
  [retained benchmark review](../../benchmark/results/retained/flat-growth-and-evaluation/2026-10-02T210323-182Z-6cbae03d/README.md).

Benchmark timings are descriptive public-work measurements, not rankings or calibration evidence.
Each snapshot retains its own source/build identity and gates; older snapshots are not evidence
that every current solver configuration passes. Strict UTC/complete-row
inputs, caller-owned schedules, scalar-versus-vectorized uncertainty, flat numerical policy and
explicitly selected historical proximal logistic fitting remain explicit differences. Bayesian fitting, worker parallelism, warm starts,
country-calendar providers and Python JSON interchange remain outside the implemented subset.

## Fixture and comparison rules

1. Read reference source and generate fixtures only from the identity in
   `tools/prophet/reference.json`. The containerized fixture runner rejects an installed distribution
   other than exactly `prophet==1.4.0`; see the [generation instructions](../../tools/prophet/README.md).
2. Keep mathematical correctness fixtures separate from Prophet compatibility fixtures. In
   particular, fixed-equation prediction tests do not establish fitted MAP parity.
3. Compare preprocessing (time/target scales, changepoints, and feature matrices), fixed-parameter
   evaluation, and fitted optimization outputs independently. Agreement in one phase does not
   imply agreement in another.
4. Use quantity-specific absolute and relative tolerances, recorded beside fixtures with a reason.
   Scaling metadata, feature indicators, and names may warrant exact equality; fitted floating-point
   values generally do not. Never loosen a tolerance to hide a different objective or preprocessing
   rule.
5. A later upstream bug fix requires an explicit baseline decision and fixture review. It must not
   silently replace the source commit above.
6. EP-096 adds stable training sorting and retained duplicate observations across supported fitting
   and evaluation paths. Date parsing remains canonical UTC and missing targets remain rejected.
   Zero-span linear/logistic failures and Python's constant-linear NaN-success bug are recorded
   explicitly; a successful invalid model is not reproduced. Featureless flat zero-span fitting
   is supported. See the [data/edge guide](../usage/data-and-edge-cases.md) and
   [correctness-gated migration cases](../../benchmark/cases/growth/linear/README.md). The
   [original native run](../../benchmark/results/retained/linear-growth-training-rows/2026-09-30T224402-292Z-4d661a06/README.md)
   preserves the former coordinate-optimizer exhaustion. The subsequent
   [Stan fit-quality closeout](../../benchmark/results/retained/linear-map-fit-quality/2026-10-02T043132-582Z-4d661a06/README.md)
   qualifies all 22 usable comparisons under the [approved requirements](../decisions/linear-map-benchmark-acceptance.md),
   with two zero-span linear exceptions and stationarity explicitly deferred to EP-097.
   This is bounded retained evidence, not blanket compatibility or a small-KKT-residual claim.
7. Regenerate fixtures with `npm run fixtures:generate` and verify with `npm run fixtures:check`.
   Fitted optimizer values use the shared canonicalizer with at most 12 significant digits;
   CPU-sensitive Fourier values remain at 12 decimal places. Never increase precision or hand-edit
   generated JSON to make one machine's result appear authoritative.
