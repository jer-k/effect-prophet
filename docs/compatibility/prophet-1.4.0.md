# Python Prophet 1.4.0 compatibility contract

## Scope

`effect-prophet` targets observable numerical behavior from the unmodified Python
`prophet==1.4.0` release. The target is fixed; it is not the upstream `main` branch and does not
advance when upstream publishes a patch.

This is a capability-by-capability target, not a claim of blanket compatibility. The current
implementation includes an ordinary least-squares (OLS) line and additive or mixed flat,
linear-piecewise, and logistic MAP lifecycles. Broader Prophet model families and fitted no-point
parameterization remain deliberately different. Until a checklist row has compatible fixture evidence, describe
this package as Prophet-inspired rather than Prophet-compatible for that capability.

Compatibility means matching documented, observable behavior where the checklist says that is
the target. It does not require Python method signatures, pandas dataframes, the CmdStanPy
backend, mutable model objects, plotting libraries, or interchange with Python's model JSON.
Those dimensions are separate and are either mapped below or deliberately different.

## Fixed reference identity

The baseline is the release identified by [`tools/prophet/reference.json`](../../tools/prophet/reference.json):

| Identity      | Value                                      |
| ------------- | ------------------------------------------ |
| Distribution  | `prophet`                                  |
| Version       | `1.4.0`                                    |
| Repository    | `https://github.com/facebook/prophet`      |
| Tag           | `v1.4.0`                                   |
| Source commit | `abf69a215604afcaa7ecb4359f592d13bf6dea9f` |

The configured `@prophet` checkout is **not** the baseline working tree. It currently describes
itself as `v1.4.0-patched-1-g79ef5ec`, two commits after the release tag. Fixture authors must
read files from the `v1.4.0` tag/source commit and must not use checkout `HEAD`. See the
[tooling instructions](../../tools/prophet/README.md) for verification.

The audit covered the release's Python `Prophet` class, diagnostics, holiday helpers, model
serialization, utilities, Matplotlib/Plotly helpers, Python tests, and the authored workflows in
`docs/_docs`. Private implementation helpers were audited where they define preprocessing,
objective, optimization, prediction, or uncertainty behavior. They are behavioral references,
not Python API-shape commitments.

## Status vocabulary

- **implemented** — the current package exposes the behavior and has the evidence linked in the
  row. This does not imply broader Prophet parity.
- **partial** — a useful subset exists, but material Prophet behavior is absent or differs.
- **planned** — the roadmap assigns the capability, but the current package does not implement it.
- **intentionally-different** — the package deliberately uses a different contract or excludes
  the capability. The reason and any future review point are stated in the row.

“Not yet covered” means there is no current compatibility evidence. A roadmap entry is not
evidence.

## Fixture and comparison rules

1. Read reference source and generate fixtures only from the identity in
   `tools/prophet/reference.json`. The containerized fixture runner rejects an installed distribution
   other than exactly `prophet==1.4.0`; see the [generation instructions](../../tools/prophet/README.md).
2. Keep mathematical correctness fixtures separate from Prophet compatibility fixtures. In
   particular, exact OLS-line tests remain useful but do not establish Prophet MAP parity.
3. Compare preprocessing (time/target scales, changepoints, and feature matrices), fixed-parameter
   evaluation, and fitted optimization outputs independently. Agreement in one phase does not
   imply agreement in another.
4. Use quantity-specific absolute and relative tolerances, recorded beside fixtures with a reason.
   Scaling metadata, feature indicators, and names may warrant exact equality; fitted floating-point
   values generally do not. Never loosen a tolerance to hide a different objective or preprocessing
   rule.
5. A later upstream bug fix requires an explicit baseline decision and fixture review. It must not
   silently replace the source commit above.
6. Stage A does not broaden date parsing, sort observations, accept duplicate timestamps, or drop
   missing targets. Compatibility fixtures must represent these differences rather than normalize
   them away unnoticed.
